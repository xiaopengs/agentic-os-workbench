## 1. 为什么是「架构决策面板」

工作台现在管的是**执行**（工作流跑没跑、技能有哪些），但缺一层**为什么这么做的记录**。
真实痛点通常是：三个月后没人记得当初为什么选了某个方案；线上出问题时无法反查到决策依据；
换人接手只能靠口头传承；Agent 生成代码时没有约束，反复写出违背既定架构的实现。

所以这个面板要解决的不是「写文档」，而是把**决策变成可检索、可追溯、可执行、可被 Agent 消费的一等公民**：

```
意图 / 约束 →【架构决策面板】→ 选定方案 → 拆成工作流 → 由技能执行 → Trace 验证 → 反哺下一次决策
```

它与现有模块形成闭环，这是它比一个独立 ADR Wiki 更有价值的地方。

## 2. 能力脑暴（6 组 · 25 项）

优先级：**P0** = MVP 必做，**P1** = 第 2 期，**P2** = 远期。
括号内是它解决的具体问题。

### A. 决策记录与结构化

| # | 能力 | 优先级 | 说明 |
|---|---|---|---|
| A1 | ADR 卡片 CRUD | **P0** | 编号 `ADR-0001`、标题、状态、上下文、结论、后果、负责人、日期 |
| A2 | MADR 结构模板 | **P0** | Context / Decision Drivers / Considered Options / Decision / Consequences / Confirmation，避免写成流水账 |
| A3 | 状态机 | **P0** | `draft → review → accepted → deprecated / superseded`，每次流转留痕 |
| A4 | 决策谱系 | P1 | `supersedes` / `supersededBy` 双向关联，展示「这条决策被谁推翻了、为什么」 |
| A5 | 外部证据挂载 | P1 | 关联 PR、设计稿、基准测试数据、Trace 链接，结论可回溯到证据 |

### B. 方案对比与权衡（面板的核心价值）

| # | 能力 | 优先级 | 说明 |
|---|---|---|---|
| B1 | 多方案并排对比矩阵 | **P0** | 行=评估维度，列=候选方案，一眼看清差异 |
| B2 | 可调权重 + 自动加权评分 | **P0** | 拖动权重实时重算总分与排名，用于检验结论是否稳健 |
| B3 | 权衡显式化 | **P0** | 每个方案强制填写「得到什么 / 失去什么 / 假设是什么」，不许只写优点 |
| B4 | 敏感性分析 | P1 | 「把性能权重翻倍，结论会不会翻转？」——暴露拍脑袋决策 |
| B5 | 成本 / 收益估算 | P2 | 一次性投入 vs 长期成本，滑块调参数看结论变化 |
| B6 | 异议与未决项 | P2 | 显式保留 dissent，避免「沉默的共识」被当成一致同意 |

### C. 评审协作与治理

| # | 能力 | 优先级 | 说明 |
|---|---|---|---|
| C1 | 评审流 + 审批人 | P1 | 草稿 → 征求意见 → 评审中 → 接受/驳回 |
| C2 | 评论 / @讨论 | P1 | 按段落评论，决议过程可追溯 |
| C3 | 共识度与分歧点 | P2 | RACI 或拇指投票，高亮分歧最大的维度 |
| C4 | 到期复核提醒 | P1 | `reviewAt` 到期在「今天要处理」区域置顶（复用工作台置顶提醒范式） |
| C5 | 决策健康度告警 | P2 | 缺后果记录、无负责人、长期未复核、状态异常 |

### D. 与现有模块联动（差异化所在）

| # | 能力 | 优先级 | 说明 |
|---|---|---|---|
| D1 | 决策 → 工作流 | **P0** | 把已接受决策的「落地事项」一键拆成工作流，回写 `/api/workflows` |
| D2 | 决策 → 技能 | P1 | 决策选定/废弃的技术映射到技能状态（active / draft / deprecated） |
| D3 | 影响面分析 | P1 | 修改某条决策时，列出受影响的工作流与技能（依赖图） |
| D4 | AI Copilot 辅助生成 | P1 | 自动起草 ADR、补全候选方案、推荐评估维度、扮演反方挑刺 |
| D5 | 决策溯源 | P2 | 从一条 Trace / 一次失败反查「当初为什么这么选」，闭环归因 |
| D6 | 架构原则库 | P2 | 反复出现的决策沉淀为团队原则，新决策录入时自动校验是否违背 |

### E. 可视化与检索

| # | 能力 | 优先级 | 说明 |
|---|---|---|---|
| E1 | 决策看板 | **P0** | 按状态分列（提议 / 评审 / 已接受 / 废弃），卡片可流转 |
| E2 | 决策时间线 | P1 | 按时间看演进，含「被取代」连线 |
| E3 | 决策地图 | P2 | 决策之间、决策与模块之间的依赖关系图 |
| E4 | 筛选与全文搜索 | P1 | 按状态 / 标签 / 负责人 / 关键词，URL 同步筛选条件 |

### F. 导出与集成

| # | 能力 | 优先级 | 说明 |
|---|---|---|---|
| F1 | 导出 Markdown ADR | P1 | 可直接提交进 Git 仓库，和代码同处一个事实源 |
| F2 | 导出 JSON / CSV | P2 | 备份、迁移、二次分析 |
| F3 | 版本 Diff | P2 | 谁在什么时候改了哪一段，支持回滚查看 |

## 3. 建议分期

### 第 1 期 · MVP（4 项，先把闭环跑通）

> 目标：**一条决策能从记录走到执行**，而不是做一个漂亮的文档库。

1. **A1 + A2 + A3**：ADR 卡片 CRUD + MADR 模板 + 状态机
2. **B1 + B2 + B3**：方案对比矩阵 + 可调权重评分 + 权衡显式化
3. **E1**：按状态分列的决策看板（窄屏改分段卡片流，不做拖拽）
4. **D1**：一键把决策拆成工作流

MVP 刻意**不做**：评论审批、AI 生成、依赖图、导出。先把「记录 → 对比 → 决策 → 执行」这条主线验证掉。

### 第 2 期

D4 AI 辅助生成 + C1/C2 评审流 + E2 时间线 + A4 谱系 + C4 复核提醒 + F1 Markdown 导出。

### 第 3 期

D3 影响面分析 + D2 技能联动 + D6 原则库 + B4 敏感性分析 + E3 决策地图 + D5 溯源。

> 与你的「重新一个个功能进行补充」节奏对齐：**一次只上一个模块 / 一组能力**，
> 每期补完先本地验证、再决定是否同步线上，不丢已有数据。

## 4. 数据模型草案

```ts
type DecisionStatus = 'draft' | 'review' | 'accepted' | 'deprecated' | 'superseded';

interface Criterion {
  id: string;
  name: string;          // 性能 / 成本 / 复杂度 / 可维护性 / 团队熟悉度 / 风险
  weight: number;        // 0–100，同一决策内归一化
  description?: string;
}

interface DecisionOption {
  id: string;
  name: string;
  summary: string;
  scores: Record<string, number>;   // criterionId → 1–5
  pros: string[];
  cons: string[];
  assumptions: string[];
}

interface Decision {
  id: string;            // ADR-0001
  seq: number;
  title: string;
  status: DecisionStatus;
  context: string;
  drivers: string[];
  criteria: Criterion[];
  options: DecisionOption[];
  decision: string;      // 最终结论（对应某个 option.id + 说明）
  consequences: { positive: string[]; negative: string[]; risks: string[] };
  owner: string;
  reviewers: string[];
  tags: string[];
  links: Array<{ type: 'workflow' | 'skill' | 'pr' | 'doc' | 'trace'; ref: string }>;
  supersedes?: string;
  supersededBy?: string;
  reviewAt?: string;
  createdAt: string;
  updatedAt: string;
  acceptedAt?: string;
}
```

数据以 `uid` 为前缀隔离（沿用现有多租户约定），落在 `StoreDriver`，
新增 key 前缀 `decision:`，**不影响已有工作流 / 技能数据**。

## 5. API 约定草案

```
GET    /api/decisions?status=&tag=&q=          列表（URL 同步筛选条件）
POST   /api/decisions                          新建（draft）
GET    /api/decisions/:id                     详情
PATCH  /api/decisions/:id                     编辑（写 history）
POST   /api/decisions/:id/review               状态流转
POST   /api/decisions/:id/comments             评论
GET    /api/decisions/:id/history              变更记录
POST   /api/decisions/:id/score                按当前权重重算排名
GET    /api/decisions/:id/impact               影响面（关联工作流 / 技能）
POST   /api/decisions/:id/to-workflow          拆成工作流（调用 /api/workflows）
GET    /api/decisions/export?format=md|json    导出
```

沿用统一信封 `ApiResp<T>` 与 `鉴权 → 校验 → 配额 → 业务 → 审计` 顺序；
决策的每次状态流转与编辑都写审计日志（复用 `/api/audit`）。

## 6. 移动端形态（必须移动优先）

本次重构已把基线改成移动优先，新模块必须遵守同一套约束：

- **看板 → 分段筛选 + 卡片流**：窄屏不做横向拖拽列，改为状态分段切换（提议 / 评审 / 已接受 / 废弃）
- **对比矩阵 → 纵向方案卡**：桌面端表格在窄屏改卡片列表，每个方案一张卡，评分用横向条形（内联 SVG，不引图表库）
- **权重调节 → 底部抽屉**，避免遮挡内容；按钮 ≥44px，输入 ≥16px
- **详情分节折叠**：Context / Options / Decision / Consequences 逐节展开
- `env(safe-area-inset-bottom)`、`overflow-x:clip`、`:focus-visible` 焦点态与现有规则一致
