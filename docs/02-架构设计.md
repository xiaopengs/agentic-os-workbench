## 0. 一句话架构

**源码态前后端分离、部署态同域自包含、存储与运行时双重驱动可替换。**

```
源码态                                  部署态（两种形态，同一套业务代码）
┌────────────────────────────┐         ┌─────────────────────────────┐
│ frontend/   Next.js 16     │         │ A. 本地最小化                 │
│ backend/    REST API 逻辑   │  ────▶  │    Node HTTP (:8787)         │
│ shared/     共享契约        │         │    + 本地 JSON 文件           │
│ agents/     AI Agent        │         │ B. EdgeOne Makers（可选）     │
│ cloud-functions/ 平台入口    │         │    Cloud Functions (/api/*)  │
└────────────────────────────┘         │    + KV / Blob               │
                                        └─────────────────────────────┘
```

**关键分界线**：`backend/` 里的业务代码**不认识任何平台**。它只认两个抽象——
`StoreDriver`（存储）与 `Env`（配置）。平台差异全部收敛在 `backend/adapter/` 与
`cloud-functions/` 这两处薄壳里。

## 1. 分层架构

自上而下单向依赖，**严禁反向调用**：

```
┌───────────────────────────────────────────────────────────────┐
│ L1 表现层   frontend/app/**/page.tsx · components/**          │
│   Next.js 16 App Router；服务端组件做首屏、客户端组件做交互     │
├───────────────────────────────────────────────────────────────┤
│ L2 状态层   frontend/lib/hooks.ts (SWR) · simulation.ts        │
│   远程状态用 SWR 缓存+重验证；本地可视化状态用 React state       │
├───────────────────────────────────────────────────────────────┤
│ L3 接入层   frontend/lib/api-client.ts                        │
│   统一 fetch 封装：信封拆包、401 跳登录、402 配额提示、SSE 流解析 │
├═════════════════════════ 网络边界 ══════════════════════════════┤
│ L4 路由层   backend/functions/router.ts                       │
│   方法+路径精确匹配 → 统一 CORS → guard 包装 → handler         │
├───────────────────────────────────────────────────────────────┤
│ L5 业务层   backend/functions/*.ts (auth/workflows/traces/…)   │
│   鉴权 → 校验 → 配额 → 业务 → 审计，顺序固定                   │
├───────────────────────────────────────────────────────────────┤
│ L6 领域层   backend/lib/  (kv/auth/quota/audit/validate/sse)   │
│   与传输方式无关的纯业务规则                                    │
├───────────────────────────────────────────────────────────────┤
│ L7 驱动层   backend/lib/store.ts · env.ts                     │
│   StoreDriver: KV | Blob | 本地文件     Env: context.env→process.env │
└───────────────────────────────────────────────────────────────┘
```

**核心原则**

- **契约单一事实源**：`shared/types.ts` 定义全部领域类型与 API 信封，前端 `lib/types.ts` 为镜像，两处改动必须同步（已通过类型检查强制）。
- **业务层零平台感知**：`functions/` 与 `lib/` 内不出现任何平台 SDK import。平台 SDK 只在 `store.ts` 的 Blob 驱动里以 `await import()` 动态加载，失败即兜底。
- **薄适配器**：`adapter/node.ts` 与 `cloud-functions/api/[[default]].ts` 都只做一件事——把各自运行时的请求翻译成统一的 `ApiCtx`，然后交给同一个 `handleRequest()`。

## 2. 技术选型与理由

| 层 | 选型 | 实际版本 | 理由 |
|---|---|---|---|
| 前端框架 | Next.js App Router | 16.3.6 | 服务端组件直出首屏；Route Group `(workbench)` 做统一鉴权布局 |
| UI | React | 19.2.0 | — |
| 样式 | Tailwind CSS | 4.3.3 | 保留原型 Design Tokens，用 CSS Variables 承载 |
| 数据请求 | SWR | 2.5.1 | 缓存、自动重验证、乐观更新，代码量远低于手写状态机 |
| 后端运行时 | Node 20+（本地）/ Cloud Functions（云） | — | 需要 `bcryptjs`、`jose` 等 npm 包，故不能用 Edge Runtime |
| 后端框架 | **无框架**，手写路由表 | — | 冷启动快、依赖极少；路由规则只有 18 条，引入 Express 不划算 |
| 鉴权 | `jose`(JWT/HS256) + `bcryptjs` + HttpOnly Cookie | jose 5.10 / bcryptjs 3.0 | 无状态、可水平扩展；Cookie 天然免疫 XSS 窃取 |
| 存储 | `StoreDriver` 抽象：KV / Blob / 本地文件 | — | 见 §4 |
| AI | OpenAI 兼容 `/chat/completions` + SSE | — | 不绑定任何厂商；本地可切模拟流 |
| 测试 | 后端冒烟（tsx）+ Playwright E2E | playwright 1.63 | 冒烟脱离平台可跑；E2E 用真实浏览器 |
| 类型 | TypeScript strict | 5.9.3 | 前后端共用 `tsc --noEmit` 门禁 |

**为什么后端不用框架**：整个 API 只有 18 条路由、7 个业务模块。手写路由表（`route(method, path, handler)` + 冒号参数匹配）不到 40 行，省掉一层依赖与冷启动开销；且这样业务 handler 的入参是自定义的 `ApiCtx`，与任何框架解耦——这正是能同时跑在 Node 与 Cloud Functions 上的前提。

## 4. 存储抽象：一个接口，三个驱动

```ts
interface StoreDriver {
  readonly name: string;
  get(key: string): Promise<string | null>;
  put(key: string, value: string): Promise<void>;
  del(key: string): Promise<void>;
  list(prefix: string): Promise<string[]>;
}
```

| 驱动 | 触发条件 | 适用场景 |
|---|---|---|
| KV | 全局命名空间存在（默认绑定名 `my_kv`，`KV_BINDING` 可覆盖） | 云上首选：强一致、低延迟、零运维 |
| Blob | KV 不存在时 | 云上兜底；SDK 通过 `await import()` 动态加载 |
| 本地文件 | `LOCAL_STORE=file`；**或平台 SDK 加载失败时自动兜底** | 本地开发、内网自托管、私有化交付 |

**驱动选择顺序**（`store.ts`）：

```
LOCAL_STORE=file ?  →  本地文件驱动
                    ↓ 否
KV 命名空间存在 ?   →  KV 驱动
                    ↓ 否
                    →  Blob 驱动
                        ↓ 加载/调用失败
                        →  本地文件驱动（自动兜底，绝不 500）
```

**为什么这个抽象值得**：去平台化时只新增了一个文件驱动实现，`kv.ts` 及以上全部代码**零改动**。上层的业务查询写法不依赖"键值对"语义之外的东西，所以换 SQLite/Redis/Postgres 也只是再加一个驱动。

### 4.1 Key 设计与多租户隔离

```ts
k.user(email)                  // user:{email}
k.session(sid)                 // session:{sid}
k.wf(uid, wfId)                // wf:{uid}:{wfId}
k.trace(uid, traceId)          // trace:{uid}:{traceId}
k.skill(uid, skillId)          // skill:{uid}:{skillId}
k.contract(uid, cid)           // contract:{uid}:{cid}
k.device(uid, did)             // device:{uid}:{did}
k.usage(uid, yyyymm)           // usage:{uid}:{yyyymm}
k.audit(uid, ts, id)           // audit:{uid}:{ts}:{id}
```

| 设计点 | 说明 |
|---|---|
| 用户维度强隔离 | 除 `user:` / `session:` 外，所有业务键第二段都是 `uid`，列表查询靠前缀扫描 |
| **uid 服务端注入** | `requireUser()` 解出 uid 后才构造 key，**客户端传入的任何 id 都只作为末段**，无法越权读写他人数据 |
| 会话与用户解耦 | `session:{sid}` 单独存，登出只删会话键，不动用户数据；`token` 里带 `sid`，因此可主动失效 |
| 用量按月分键 | `yyyymm` 后缀让月结与重置都是天然免费的 |
| 审计键自带时间戳 | `audit:{uid}:{ts}:{id}` 前缀扫描即按时间有序，无需二次排序 |

## 5. 请求生命周期（以 `POST /api/workflows` 为例）

```
浏览器 fetch('/api/workflows', { method:'POST', credentials:'include' })
  │
  ├─ 本地形态：Next.js dev server → 直连 http://127.0.0.1:8787（跨域，带 Cookie）
  │   后端 Node 适配器：OPTIONS 预检走快通道 → 收集 body → 组 ApiCtx
  │
  └─ 云形态：同域 /api/* → cloud-functions/api/[[default]].ts → onRequest
       → 组 ApiCtx
  │
  ▼
handleRequest(ctx)
  ├─ 1. 解析 origin（在 guard 之外，保证错误响应也带 CORS 头）
  ├─ 2. segs = path.split('/')  →  路由表按 方法+段数+段字面量 精确匹配
  ├─ 3. guard(handler)  捕获一切异常 → 结构化错误信封，绝不裸 500
  └─ 4. 统一附加 CORS 头（成功与失败一视同仁）
  │
  ▼
createWorkflow(ctx)
  ├─ requireUser(ctx, repo)        → 401 未登录 / 解出 uid 与 plan
  ├─ readJsonBody()                → 400 非法 JSON
  ├─ validateWorkflowInput()       → 400 VALIDATION_ERROR（中文提示）
  ├─ repo.upsertWorkflow(uid, wf)  → 写 wf:{uid}:{wfId}
  ├─ writeAudit(repo, uid, 'workflow.create', ...)  → 写 audit:{uid}:{ts}:{id}
  └─ ok(workflow)                  → 201 { ok:true, data:Workflow }
```

**固定的业务顺序**：`鉴权 → 校验 → 配额 → 业务 → 审计`。这个顺序不是随意的——
配额必须在校验通过之后（无效请求不该扣额度），审计必须在业务成功之后（失败的操作不该留成功记录）。

### 5.1 AI Copilot 的流式路径（唯一的例外顺序）

```
POST /api/ai/copilot
  ├─ 401 鉴权
  ├─ 400 入参校验
  ├─ 503 AI Gateway 预检（先连上游，可用性不消耗额度）
  ├─ 402 配额拦截 ← 必须在流开始前
  ├─ 审计
  └─ 200 + text/event-stream  逐帧推送
```

> **铁律**：配额必须在响应头以 200 提交**之前**拦截。一旦 SSE 开始，HTTP 状态码就无法再改成 402。
> 因此顺序是 `Gateway 预检 → 配额 → 开流`，而不是常见的"先开流再说"。同时配额扣减放在预检之后——上游不可用时不应消耗用户额度。

## 6. 统一响应与错误码

```ts
type ApiOk<T>  = { ok: true;  data: T }
type ApiErr    = { ok: false; error: { code: string; message: string } }
type ApiResp<T> = ApiOk<T> | ApiErr
```

| HTTP | code | 触发场景 | 前端行为 |
|---|---|---|---|
| 400 | `VALIDATION_ERROR` | 入参缺失/格式非法/枚举越界 | 表单行内提示 |
| 401 | `UNAUTHORIZED` | 未登录、token 无效或已登出 | 清会话 → 跳 `/login` |
| 402 | `QUOTA_EXCEEDED` | 当月 runs 超上限 | 弹升级引导，不重试 |
| 404 | `NOT_FOUND` | 路由或资源不存在 | 展示空态 |
| 409 | `CONFLICT` | 邮箱已注册 | 表单行内提示 |
| 500 | `SERVER_MISCONFIG` | `JWT_SECRET` 缺失（**故意抛错**） | 全屏配置错误页 |
| 503 | `AI_UNAVAILABLE` | 上游不可用 / 未配置 | 可重试提示 + 修复指引 |

`SERVER_MISCONFIG` 的设计意图：宁可启动即失败，也不允许用硬编码默认密钥悄悄上线。

## 7. 关键流程

### 7.1 注册 → 播种 → 首屏

```
POST /auth/register
  ├─ 校验邮箱格式 + 密码强度（≥8 位，含字母与数字）
  ├─ 邮箱查重 → 409
  ├─ bcrypt.hash(password, 10)
  ├─ 写 user:{email}
  ├─ 写 session:{sid}，签 JWT（sub=uid, sid, plan, exp=7d）
  ├─ 写 Set-Cookie: token=...; HttpOnly; SameSite=Lax; Path=/
  └─ seedUserData(uid)  ← 幂等播种
       1 条示例工作流 + 5 条 Trace + 4 个技能 + 3 个合同 + 4 台设备 + 当月用量基线
```

**播种原则**：只在首次执行（`user.seeded` 标记），数据为**固定字面量**而非随机生成——
这样每个新用户的 Dashboard 都有稳定、可复现的内容，也让 E2E 断言有据可依。
所有播种数据都是真实写入持久化存储的，不是前端 mock。

### 7.2 会话保持

```
登录 → Set-Cookie(HttpOnly)
     → 之后每次请求浏览器自动携带
     → 后端 requireUser() 读 Cookie；Cookie 缺失时回退 Authorization: Bearer
     → 校验 JWT 签名与过期 → 再查 session:{sid} 是否存在（支持主动登出失效）
```

**Cookie 优先、Bearer 兜底**：Cookie 服务于浏览器（免疫 XSS 窃取），Bearer 服务于
CLI / 移动端 / E2E 测试脚本。

### 7.3 配额扣减

```
consume(repo, user, { runs, tokens })
  ├─ 读 usage:{uid}:{yyyymm}（不存在则按 0 起算）
  ├─ next = current + delta
  ├─ next.runs > PLAN_LIMITS[plan]  →  抛 402 QUOTA_EXCEEDED
  └─ 写回 usage:{uid}:{yyyymm}
```

| 计划 | runs/月 |
|---|---|
| `free` | 100 |
| `pro` | 10000 |

### 7.4 前端数据流

```
useWorkbench()  ─┬─ SWR('/api/workflows')  ─┐
                 ├─ SWR('/api/traces')      │  并行取数
                 ├─ SWR('/api/skills')      │  统一信封拆包
                 ├─ SWR('/api/contracts')   │  401 → 跳登录
                 ├─ SWR('/api/devices')     │  402 → 配额提示
                 └─ SWR('/api/usage')      ─┘
                        │
                        ▼
              useMemo 派生 KPI / 生命周期节点状态 / P95
                        │
                        ▼
        纯展示组件（KpiGrid / LifecycleCard / LiveTrace …）
```

**原则**：绝不在前端硬编码业务数字。KPI 的 Contract 数就是 `/api/contracts` 的长度、
Skills 数就是 `/api/skills` 的长度、P95 由真实 trace 耗时算出——这样"数据是真是假"不需要靠人去辨认。
仿真实验台内部的指标微动（内存/NPU 波动）属于**可视化演示状态**，由 `lib/simulation.ts` 在浏览器内驱动，与服务端数据严格分开。

## 8. 契约优先（Contract-First）

```
shared/types.ts   ← 唯一事实源
  ├─ 领域类型：User / Workflow / Trace / Skill / Contract / Device / Usage / AuditLog
  ├─ 请求类型：CopilotRequest / 各 CRUD 入参
  ├─ 响应信封：ApiResp<T>
  └─ 常量：PLAN_LIMITS / FREE_LIMIT / PRO_LIMIT / AI_GATEWAY_ENV_KEYS

frontend/lib/types.ts   ← 镜像（前端构建不能跨出 frontend/ 目录）
  必须与 shared 保持一致，由 tsc 门禁 + 人工 review 双重保证
```

**为什么镜像而不是直接引用**：Next.js 应用根目录是 `frontend/`，`tsconfig` 的 `baseUrl`
与打包边界都在其内，跨目录 import 会引入构建与部署的复杂度。代价是"两处同步"，
收益是前端可独立构建、独立部署。两处的类型名与字段必须逐一对齐。

## 9. 构建与部署架构

```
scripts/build-deploy.mjs
  ├─ 清理 dist/
  ├─ 复制 frontend/ → dist/ 根         （app/ components/ lib/ styles/ public/）
  ├─ 复制 backend/ shared/ agents/     （保持 ../../ 相对路径不变）
  ├─ 复制 cloud-functions/ + edgeone.json + .env.example
  └─ 合并 package.json
       dependencies         = 前端 deps + 根 deps
       optionalDependencies = 平台 SDK（@edgeone/pages-blob）
       devDependencies      = 前端 + 根
```

**相对路径不变式**：`cloud-functions/api/[[default]].ts` 内写的是 `../../backend/...`，
在 `dist/` 下解析为 `dist/backend/...`，与源码态 `cloud-functions/ → backend/` 一致——
因此构建脚本**不需要改写任何 import**。

## 10. 安全设计

| 面 | 措施 |
|---|---|
| 密码 | bcrypt（cost 10），永不明文落库；错误信息不区分"用户不存在/密码错"，避免枚举 |
| 会话 | HttpOnly + SameSite=Lax Cookie；JWT HS256 签名；服务端维护会话表以支持主动失效 |
| 密钥 | `JWT_SECRET` 生产缺失直接 500，杜绝默认密钥上线 |
| 越权 | 所有业务 key 由服务端从会话解出的 uid 构造，客户端 id 只能作为末段 |
| 注入 | 手写参数化校验（`validate.ts`），不拼接任何用户输入到 key 结构里 |
| 洪泛 | trace 写入节流；SSE 带心跳与客户端中断联动（abort 同步切断上游） |
| CORS | 白名单式回显 origin；错误响应同样附 CORS 头（否则前端拿不到 401/402/409 真实码） |
| 错误泄露 | 上游错误截断至 300 字符；内部异常统一转结构化信封，不吐栈 |

## 11. 降级与容错

| 场景 | 行为 |
|---|---|
| 平台 SDK 未安装 | `await import()` 失败 → 本地文件驱动兜底，服务照常 |
| KV 不存在 | 自动降级 Blob |
| 文件不可写 | 内存态运行 + 控制台告警，不中断请求 |
| AI Gateway 未配置 | 未开 mock → 503 `AI_UNAVAILABLE`（非 500），文案给出两种修复路径；`LOCAL_AI_MOCK=1` → 本地模拟 SSE 流 |
| 客户端中途断开 | abort 传播至上游 fetch，及时释放连接 |
| `JWT_SECRET` 缺失 | 生产 500 `SERVER_MISCONFIG`；开发用固定值 + 打印警告 |
| 前端接口 401 | 清会话 → 跳登录，不回放失败请求 |

## 附录 A · 原型阶段架构（v1.0，已归档）

首版交付物是单文件 `workbench.html`，采用**五层架构**：L1 视图层（静态 HTML+CSS）
→ L2 渲染层（`render*` 纯函数）→ L3 状态与模拟引擎层（单一 `state` + 3 个定时器）
→ L4 数据接入层（`DataBridge`：资料库 SDK ⇄ localStorage ⇄ 内置演示数据）
→ L5 宿主层（WorkBuddy 资料库托管）。

它承担的是**视觉与交互规格的定义**工作：Design Tokens、区域布局、图标体系、
模拟引擎节奏。函数调用链严格无环（`refreshAll()` 为唯一调度入口，渲染函数零互调），
数据表用 `data-sp-bindable` 绑定标记。

**为什么重构**：该架构的数据只存在于 localStorage 或平台数据表，没有账号体系、
服务端校验、配额与审计——这些是商业化产品的地基，无法在单文件内补齐。
但原型的**视觉规格被完整保留**：Design Tokens 原样进入 Tailwind 主题，
组件布局与交互节奏在 v2 中逐区域复刻。

  原型阶段的测试与修正记录见 [04-测试用例与对比修正报告](./04-测试用例与对比修正报告.md)（标注为原型阶段）。
