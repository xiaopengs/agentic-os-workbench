# 05 · 前后端分离架构选型与商业化技术方案

> 目标：把当前「单文件 demo 网页」升级为**端到端可交付的商业化 SaaS 产品**。
> 决策人：Makers 开发专家团主理人 · 2026-09-28
> 状态：**已实施完成**。选型结论（方案 A）与本文一致；
> 实施过程中的一处修正见文末「九、实施后的两处修正」。

---

## 一、现状诊断：为什么它还只是 demo

| 维度 | 当前状态 | 商业化要求 | 差距 |
|---|---|---|---|
| 数据 | 模拟引擎生成 + localStorage | 服务端持久化、多租户隔离 | ❌ 刷新即假数据 |
| 鉴权 | 无 | 注册/登录/会话/权限 | ❌ 无账号体系 |
| 后端 | 无（纯前端 SDK 直读写） | 独立 REST API 服务 | ❌ 业务逻辑在客户端 |
| 计费 | 无 | 配额 + 用量统计 + 订阅 | ❌ 无法商业化 |
| 可观测 | 无 | 审计日志、错误追踪 | ❌ |
| 部署 | 资料库静态页面 | 前端 + 后端流水线部署 | ❌ |

**结论**：需要一次架构级重构，而非在 HTML 上打补丁。

## 二、架构选型（三选一，果断推荐 A）

| 方案 | 描述 | 优势 | 劣势 | 结论 |
|---|---|---|---|---|
| **A. 同仓库逻辑分离 + 统一部署** ✅ | `frontend/` Next.js 16 + `backend/` REST API，共享 `shared/` 契约，API 走同域 `/api/*` | 零跨域；HttpOnly Cookie 会话天然共享；一次部署前后端原子生效；运维成本最低；契约可随时拆分为独立服务 | 前后端处于同一部署单元（但代码、契约、职责完全分离） | **已实施** |
| B. 双项目物理分离 | 前端一个项目，后端 API 另一个独立项目 | 物理隔离彻底、独立扩缩容 | 跨域配置；Cookie 需 `SameSite=None` 或改用 Bearer Token；两次部署易版本错配；成本翻倍 | 暂不采用 |
| C. Next.js 全栈单体（API Routes） | 前后端都写在 Next.js 内 | 最省事 | 不满足「前后端分离式」要求；后端无法被其他客户端（CLI/移动端）复用 | 否决 |

**推荐方案 A 的理由**：
1. 商业化早期最重要的是**交付速度与一致性**，同域部署消灭了整类跨域/Cookie 问题；
2. 通过 `shared/` 目录定义**契约优先**（Contract-First），后端保留为独立服务，
   将来要拆成 B 方案只需换 baseURL，前端零改动；
3. 成本可控（单一项目额度）。

**实施中的关键修正**：原计划的「Cloud Functions 后端」在实施后被**进一步解耦为
运行时无关的 REST 服务**——同一套业务代码既跑在 Node HTTP（本地），也跑在
Cloud Functions（云上），通过 `StoreDriver` 与 `ApiCtx` 两个抽象隔离平台差异。
这使得「本地最小化部署」成为可能，也顺带让测试不再依赖平台。详见 §九。

## 四、数据模型（KV Key 设计）

```
user:{email}              → User { id, email, passHash, plan, createdAt }
session:{sid}             → Session { userId, exp }
wf:{uid}:{wfId}           → Workflow
trace:{uid}:{traceId}     → Trace
skill:{uid}:{skillId}     → Skill
contract:{uid}:{cid}      → Contract
device:{uid}:{did}        → Device
usage:{uid}:{yyyymm}      → { runs, tokens, costCents }
audit:{uid}:{ts}:{id}     → AuditLog
```

**多租户隔离**：除 `user:` / `session:` 外，所有业务键第二段都是 `uid`，
由 `requireUser()` 从会话解出后**服务端注入**；客户端传入的 id 只能作为末段，无法越权。

**会话与用户解耦**：`session:{sid}` 单独存储，登出只删会话键，
使 JWT 获得可主动失效的能力（纯 JWT 做不到）。

## 五、API 契约（Contract-First）

### 鉴权
```
POST /api/auth/register   { email, password }        → { user, token }
POST /api/auth/login      { email, password }        → { user, token }
POST /api/auth/logout                                → { ok }
GET  /api/auth/me                                    → { user }
```

### 业务资源
```
GET    /api/workflows            → Workflow[]
POST   /api/workflows            → Workflow
GET    /api/workflows/:id        → Workflow
PATCH  /api/workflows/:id        → Workflow
DELETE /api/workflows/:id        → { ok }

GET    /api/traces               → Trace[]
POST   /api/traces               → Trace

GET    /api/skills               → Skill[]
GET    /api/contracts            → Contract[]
GET    /api/devices              → Device[]
GET    /api/usage                → Usage
GET    /api/audit                → AuditLog[]
GET    /api/health               → { ok: true }
```

### AI
```
POST /api/ai/copilot   { messages, context }  → SSE 流式
```

**统一响应规范**：
```ts
type ApiOk<T>   = { ok: true; data: T }
type ApiErr     = { ok: false; error: { code: string; message: string } }
type ApiResp<T> = ApiOk<T> | ApiErr
```

## 九、实施后的两处修正

原方案在落地后有两处必要修正，记录在此以免文档与实现脱节：

### 修正 1：后端运行时抽象化（方案 A 的加强版）

原计划后端**只能**跑在 EdgeOne Cloud Functions。实施后改为：

| 抽象 | 作用 |
|---|---|
| `StoreDriver`（get/put/del/list） | KV → Blob → 本地文件三级驱动，前者失效自动兜底 |
| `ApiCtx` + `handleRequest()` | 业务逻辑的唯一定义处；平台差异收敛到 `adapter/node.ts` 与 `cloud-functions/` |

**收益**：
- 交付不再被平台登录阻塞（本地一条命令即可运行）
- 测试脱离平台，每次改动可立刻验证
- 私有化 / 内网交付成为可能
- 平台 SDK 降为 `optionalDependencies`，本地部署无需安装

**代价**：多维护一个适配器（约 150 行），以及"契约两处镜像"的同步成本。

### 修正 2：AI 能力的本地降级

AI 原方案强依赖平台注入的 AI Gateway 凭据。实施后补充两条路径：

| 场景 | 行为 |
|---|---|
| 配了 `AI_GATEWAY_API_KEY` / `AI_GATEWAY_BASE_URL` | 走真实模型，本地云端一致 |
| 未配 + `LOCAL_AI_MOCK=1` | 本地模拟流，产出与 OpenAI **完全同构**的 SSE 帧，流式协议 / 配额 / 审计 / 前端渲染全链路可离线验证 |
| 未配 + 未开 mock | 503 `AI_UNAVAILABLE`（非 500），文案给出两种修复路径 |

**关键点**：模拟流发的是标准 `data: {"choices":[{"delta":{"content":"…"}}]}` 帧，
所以 `iterChatStream()` 与前端渲染代码一行都不用改——换真模型只需改环境变量。
