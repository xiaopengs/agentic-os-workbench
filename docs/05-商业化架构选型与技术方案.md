# 05 · 前后端分离架构选型与商业化技术方案

> 目标：把当前「单文件 demo 网页」升级为**端到端可交付的商业化 SaaS 产品**。
> 决策人：Makers 开发专家团主理人 · 2026-09-28

---

## 一、现状诊断：为什么它还只是 demo

| 维度 | 当前状态 | 商业化要求 | 差距 |
|---|---|---|---|
| 数据 | 模拟引擎生成 + localStorage | 服务端持久化、多租户隔离 | ❌ 刷新即假数据 |
| 鉴权 | 无 | 注册/登录/会话/权限 | ❌ 无账号体系 |
| 后端 | 无（纯前端 SDK 直读写） | 独立 REST API 服务 | ❌ 业务逻辑在客户端 |
| 计费 | 无 | 配额 + 用量统计 + 订阅 | ❌ 无法商业化 |
| 可观测 | 无 | 审计日志、错误追踪 | ❌ |
| 部署 | 资料库静态页面 | 前端 + 后端流水线部署 | ❌ |

**结论**：需要一次架构级重构，而非在 HTML 上打补丁。

---

## 二、架构选型（三选一，果断推荐 A）

| 方案 | 描述 | 优势 | 劣势 | 结论 |
|---|---|---|---|---|
| **A. 同仓库逻辑分离 + 统一部署** ✅ | `frontend/` Next.js 16 + `backend/` Cloud Functions，共享 `shared/` 契约，部署到同一 EdgeOne Makers 项目，API 走 `/api/*` 同域 | 零跨域；HttpOnly Cookie 会话天然共享；一次部署前后端原子生效；运维成本最低；契约可随时拆分为独立服务 | 前后端处于同一部署单元（但代码、契约、职责完全分离） | **推荐** |
| B. 双项目物理分离 | 前端一个 Makers 项目，后端 API 另一个独立项目 | 物理隔离彻底、独立扩缩容 | 跨域配置；Cookie 需 `SameSite=None` 或改用 Bearer Token；两次部署易版本错配；成本翻倍 | 暂不采用 |
| C. Next.js 全栈单体（API Routes） | 前后端都写在 Next.js 内 | 最省事 | 不满足「前后端分离式」要求；后端无法被其他客户端（CLI/移动端）复用 | 否决 |

**推荐方案 A 的理由**：
1. 商业化早期最重要的是**交付速度与一致性**，同域部署消灭了整类跨域/Cookie 问题；
2. 通过 `shared/` 目录定义**契约优先**（Contract-First），后端保留为独立 Cloud Functions，将来要拆成 B 方案只需换 baseURL，前端零改动；
3. 成本可控（单一项目额度）。

## 三、技术栈定稿

| 层 | 选型 | 版本/说明 |
|---|---|---|
| 前端框架 | Next.js（App Router） | 16.x + TypeScript |
| 样式 | Tailwind CSS | v4，沿用既有 Design Tokens |
| 数据请求 | SWR | 缓存 + 自动重验证 + 乐观更新 |
| 后端运行时 | EdgeOne Cloud Functions（Node.js） | 需 npm 包（bcryptjs / jose），故不用 Edge Functions |
| 后端框架 | Express 风格路由（无框架轻量实现） | 冷启动快、依赖少 |
| 主存储 | KV Storage | 平台原生、零运维、低延迟 |
| 文件存储 | Blob Storage | 制品/附件，首次写入自动创建 |
| 鉴权 | JWT（jose）+ bcryptjs + HttpOnly Cookie | Middleware 统一守卫 |
| AI | `agents/` + AI Gateway | `AI_GATEWAY_API_KEY`/`AI_GATEWAY_BASE_URL` 平台自动注入，SSE 流式 |
| 契约 | `shared/` TypeScript 类型 + OpenAPI 摘要 | 前后端共享单一事实源 |
| 测试 | Playwright E2E + Vitest 单元 | 覆盖全链路 |

## 四、数据模型（KV Key 设计）

```
user:{email}              → User { id, email, passHash, plan, createdAt }
session:{sid}             → Session { userId, exp }
wf:{uid}:{wfId}           → Workflow
trace:{uid}:{traceId}     → Trace
skill:{uid}:{skillId}     → Skill
contract:{uid}:{cid}      → Contract
usage:{uid}:{yyyymm}      → { runs, tokens, costCents }
audit:{uid}:{ts}:{id}     → AuditLog
```

**多租户隔离**：所有业务数据以 `userId` 为前缀，服务端强制注入，客户端不可伪造。

---

## 五、API 契约（Contract-First）

### 鉴权
```
POST /api/auth/register   { email, password }        → { user, token }
POST /api/auth/login      { email, password }        → { user, token }
POST /api/auth/logout                                → { ok }
GET  /api/auth/me                                    → { user }
```

### 业务资源
```
GET    /api/workflows            → Workflow[]
POST   /api/workflows            → Workflow
GET    /api/workflows/:id        → Workflow
PATCH  /api/workflows/:id        → Workflow
DELETE /api/workflows/:id        → { ok }

GET    /api/traces               → Trace[]
POST   /api/traces               → Trace

GET    /api/skills               → Skill[]
GET    /api/contracts            → Contract[]
GET    /api/usage                → Usage
GET    /api/audit                → AuditLog[]
```

### AI
```
POST /api/ai/copilot   { messages, context }  → SSE 流式
```

**统一响应规范**：
```ts
type ApiOk<T>   = { ok: true; data: T }
type ApiErr     = { ok: false; error: { code: string; message: string } }
type ApiResp<T> = ApiOk<T> | ApiErr
```

## 六、商业化能力矩阵

| 能力 | MVP 实现 |
|---|---|
| 多租户 | userId 前缀隔离 + 服务端强制注入 |
| 配额计费 | 免费版 100 runs/月，Pro 10000 runs/月，`usage:{uid}:{yyyymm}` 计数，超额 402 |
| 审计日志 | 关键写操作落 `audit:` 键，可回溯 |
| 订阅计划 | `user.plan = free \| pro`，配额中间件按 plan 分流 |
| 可观测 | 结构化日志 + 错误码体系 |
