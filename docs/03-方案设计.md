## 2. 布局结构

三段式 Grid，断点内切换：

```
≥1280px  grid-template:
           "topnav topnav topnav"  60px
           "sidenav main  aside"   1fr / 208px 1fr 328px
         └ header.topnav    白底 sticky
         └ nav.sidenav     白底，含底部品牌卡

         └ aside.aside     328px，4 张卡片纵排

<900px       单列；侧边栏收为汉堡抽屉；KPI 4→2 列；生命周期节点纵排
```

## 4. 前端实现方案

### 4.1 组件分层

```
app/
 ├ layout.tsx                    全局 Provider：AuthProvider + ToastHost
 ├ login/ · register/            独立于工作台外壳的全屏页
 ├ (workbench)/layout.tsx        工作台外壳（含登录守卫 + AppShell 三栏）
 └ (workbench)/
    ├ page.tsx                   总览：PageHeader + KpiGrid + LifecycleCard
    │                            + row-2col(SimulationLab, LiveTrace + RecentWorkflows)
    ├ workflows/ · skills/ · contracts/ · devices/ · settings/
```

组件分三类，**严格不混用职责**：

| 类别 | 位置 | 特征 |
|---|---|---|
| 布局组件 | `components/layout/` | 只负责骨架与导航，不含业务数据 |
| 业务组件 | `components/dashboard/` · `aside/` · `modals/` | 接收数据 props，**纯展示**，不发请求 |
| 基础 UI | `components/ui/` | PageHeader、Button、Card、Toast、Skeleton 等 |

### 4.2 状态管理

| 状态类型 | 方案 | 例子 |
|---|---|---|
| 远程数据 | SWR（`lib/hooks.ts`） | workflows / traces / skills / contracts / devices / usage / audit |
| 会话状态 | React Context（`lib/auth.tsx`） | 当前用户、登录态、登出 |
| 全局提示 | 轻量事件总线（`lib/toast-bus.ts`） | toast 消息 |
| 可视化演示态 | `lib/simulation.ts` | 端侧指标微动、阶段进度、计时 |
| 局部交互态 | `useState` | 弹窗开关、表单字段 |

**分界原则**：凡是"应该落库的"一律走 SWR + API；凡是"纯属展示节奏的"
（如内存数值轻微跳动）留在浏览器内。两者在 UI 上明确区分，避免让人误以为假数据是真的。

### 4.3 数据派生

KPI、生命周期节点状态、P95 等都不是独立请求，而是**从已有数据派生**：

```ts
// 示意：真实实现见 app/(workbench)/page.tsx
const p95 = useMemo(() => percentile(data.traces.map(t => t.cost), 95), [data.traces]);
const p95Trend = useMemo(() => trendPct(data.traces), [data.traces]);
```

好处：一次请求驱动多处展示，避免 N+1；且数值之间天然自洽（KPI 的合同数
与合同页列表长度**必然一致**，因为它们读的是同一份数据）。

### 4.4 API 客户端（`lib/api-client.ts`）

```ts
API_BASE = (process.env.NEXT_PUBLIC_API_BASE || '/api').replace(/\/+$/, '')
```

| 能力 | 实现 |
|---|---|
| 信封拆包 | 自动判 `ok`；失败时抛结构化错误对象（含 code） |
| 会话携带 | `credentials: 'include'`，Cookie 自动透传 |
| 401 处理 | 清会话 → 跳 `/login` |
| 402 处理 | 弹配额提示，不重试 |
| SSE | `streamSSE()`：`ReadableStream` + 按行解析 `data:` 帧，兼容整包 JSON |
| 请求头 | 自动附带 `makers-conversation-id`（AI 会话追踪） |

## 5. 后端实现方案 · 路由与中间件

### 5.1 路由表（18 条，`functions/router.ts`）

```
POST   /auth/register        POST /auth/login     POST /auth/logout   GET /auth/me
GET    /workflows            POST /workflows
GET    /workflows/:id        PATCH /workflows/:id  DELETE /workflows/:id
GET    /traces               POST /traces
GET    /skills               GET /contracts        GET /devices
GET    /usage                GET /audit
POST   /ai/copilot
GET    /health
```

匹配算法：路径按 `/` 切段 → 逐段比对（`:xxx` 段吞任意值并解出参数）→ 段数必须相等。
手写实现不到 40 行，比引入框架更可控。

### 5.2 统一中间件（`handleRequest`）

```
1. 解析 origin（放在 guard 之外，保证错误响应也带 CORS 头）
2. OPTIONS 预检 → 204（Allow-Headers 含 Content-Type, Authorization, makers-conversation-id）
3. 构造 ApiCtx { env, method, path, segs, params, query, req, raw }
4. guard(handler) → 捕获一切异常 → 结构化错误信封
5. 统一附加 CORS 头
```

### 5.3 业务 Handler 固定顺序

```
鉴权 requireUser() → 校验 validate*() → 配额 consume() → 业务 → 审计 writeAudit()
```

顺序约束的理由：
- 配额在校验**之后**——无效请求不该扣额度
- 审计在业务**成功之后**——失败操作不该留成功记录
- AI 流式接口例外（`Gateway 预检 → 配额 → 开流`），理由见 02 文档 §5.1

## 6. 后端实现方案 · 鉴权

```
注册  bcrypt.hash(pwd, 10) → 写 user:{email}
      → 生成 sid → 写 session:{sid}
      → 签 JWT { sub: uid, sid, plan, exp: 7d }
      → Set-Cookie: token=...; HttpOnly; SameSite=Lax; Path=/; Max-Age=7d
      → seedUserData(uid)

登录  按 email 取 user → bcrypt.compare（失败统一返回「邮箱或密码错误」，不区分）
      → 新 sid + 新会话 → Set-Cookie

鉴权  requireUser(ctx, repo)
      ① 读 Cookie token（缺失则读 Authorization: Bearer）
      ② jose.jwtVerify 校验签名与过期
      ③ 查 session:{sid} 是否存在 → 不存在即视为已登出 → 401
      ④ 返回 { id, email, plan }

登出  删除 session:{sid} + 清 Cookie
```

**密码强度规则**：≥8 位且同时含字母与数字。中文错误提示，400 `VALIDATION_ERROR`。

**为什么不区分"用户不存在"与"密码错误"**：避免账号枚举攻击。
前端表单对两种情况给出同一句提示。

**为什么 JWT 之外还要会话表**：纯 JWT 无法主动失效。加上 `session:{sid}`
之后，登出、改密、封号都能立刻生效——这是商业化产品的必要能力。

## 7. 后端实现方案 · 校验 / 配额 / 审计

### 7.1 入参校验（`lib/validate.ts`）

手写字段级校验，返回中文错误信息。以工作流为例：

| 字段 | 规则 |
|---|---|
| `name` | 必填，1–80 字符 |
| `category` | 必填 |
| `description` | 可选，≤500 字符 |
| `devices` / `steps` | 非负整数 |
| `coverage` | 0–100 |
| `duration` | 非负整数（分钟） |
| `status` | 枚举：`running` / `done` / `failed` / `queued` |
| `env` | 枚举：`dev` / `staging` / `prod` |

错误统一为 `400 VALIDATION_ERROR`，`message` 形如「状态 取值非法，可选值：running / done / failed / queued」——
足够定位到具体字段与可选值。

### 7.2 配额（`lib/quota.ts`）

```
consume(repo, user, { runs, tokens })
  读 usage:{uid}:{yyyymm} → 累加 → 超限抛 402 → 写回
```

| 计划 | runs/月 | 常量 |
|---|---|---|
| free | 100 | `FREE_LIMIT` |
| pro | 10000 | `PRO_LIMIT` |

超额响应带具体数字：「本月配额已耗尽（100/100 次）。请升级 Pro（10000 次/月）或等待下月重置。」
用量按 `yyyymm` 分键，月结与重置天然免费。

### 7.3 审计（`lib/audit.ts`）

```
writeAudit(repo, uid, action, meta) → audit:{uid}:{ts}:{id}
```

记录动作：注册、登录、登出、工作流创建/更新/删除、AI 对话。
键自带时间戳，前缀扫描即按时间有序。前端 Attention 卡片直接消费这份数据，
因此「告警列表」与「审计日志」是同一份事实，不会出现两张皮。

## 8. 后端实现方案 · AI 流式

### 8.1 消息装配（`lib/copilot.ts`）

`buildCopilotMessages(messages, context)` 把前端历史 + 场景上下文装配成
OpenAI 兼容的消息数组；`copilotTarget(context)` 决定场景标题与预设提示。

### 8.2 上游调用（`lib/ai-gateway.ts`）

| 关注点 | 实现 |
|---|---|
| 协议 | OpenAI 兼容 `POST {baseUrl}/v1/chat/completions`（自动兼容 baseUrl 已带 `/v1`） |
| 凭据 | 只从 `Env` 读，绝不硬编码；生产由平台注入，自托管自填 |
| 超时 | 60s `AbortController` |
| 中断联动 | 客户端 `signal` → 同步 abort 上游 fetch |
| 流解析 | `iterChatStream()` 逐行解析 `data:` 帧，`[DONE]` 结束；单行解析失败静默跳过 |
| 错误归类 | 401/403 → 鉴权失败；429 → 限流；其他 → 带截断详情的 503 |

### 8.3 本地模拟流（`openLocalMockChat`）

未配置 Gateway 且 `LOCAL_AI_MOCK=1` 时启用，目的：**离线也能端到端验证**流式协议、
配额扣减、审计落库、前端渲染全链路。

它产出与 OpenAI **完全同构**的 SSE 帧：

```
data: {"choices":[{"delta":{"content":"…"},"finish_reason":null}]}
…
data: {"choices":[{"delta":{},"finish_reason":"stop"}],"usage":{…}}
data: [DONE]
```

因此 `iterChatStream()` 与前端渲染代码**一行都不用改**——换真模型只需改环境变量。

### 8.4 前端流式渲染

```
streamSSE({ path:'/ai/copilot', body, signal, onDelta, onUsage })
  → ReadableStream reader + TextDecoder（stream:true）
  → 缓冲按行切分 → data: 帧 JSON.parse → onDelta(delta) → setState 追加
  → 支持中途 abort
```

同时兼容上游返回整包 JSON 的情况（非流式兜底），保证任何后端实现都能渲染。

## 9. 前端鉴权与路由保护

```
(workbench)/layout.tsx
  └─ useAuth() → loading 时显示骨架
              → 未登录 → redirect('/login')
              → 已登录 → <AppShell>{children}</AppShell>
```

## 附录 A · 原型阶段实现方案（v1.0，已归档）

首版 `workbench.html` 的实现要点，保留作为视觉对照基准：

**构建方式**：单文件 HTML（约 3500–4000 行），CSS/JS 全内联，零外部依赖；
单文件体量超限时采用「先写完整骨架，再按模块分 3 批增量写 JS」的策略，
每批写入后文件保持可运行。

**模拟引擎**：3 个独立定时器驱动整个页面的"活性"——
`tickClock`(1s) 走时钟并微调端侧指标；`tickTrace`(4s) 产生新 Span 并写入数据表；
`tickProgress`(2.5s) 推进测试阶段、Next Step 流转、Canary 灰度递增。
渲染函数之间零互调，统一由 `refreshAll()` 调度。

**数据接入**：`DataBridge` 维护 SDK → localStorage → 内置演示数据的三级降级链，
保证任何环境下打开都不白屏。数据表用 `data-sp-bindable` + `data-sp-database-id`
绑定标记关联平台数据表。

**逐区域实现规格**：KPI 卡的图标/数值/趋势、Lifecycle 六节点的图标配色与状态胶囊五态、
Simulation Lab 的手机模型与 2×2 指标卡、Live Trace 的行结构与耗时归一化映射、
Recent Workflows 的卡片元信息、右栏四卡的完整结构与交互——这些规格在 v2 中
被**逐区域复刻**到 React 组件里，视觉上保持一致。

**与 v2 的本质差异**：原型的全部数据都是浏览器内生成或平台表存储的，
没有账号体系、服务端校验、配额与审计。v2 保留视觉规格、替换数据来源，
把"看起来活的页面"变成"真的在跑的系统"。
